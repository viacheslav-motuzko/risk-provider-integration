# Fixed decisions D1-D12 (rationale)

Decided with the user and revised once after an independent review. Do not change silently; if you think one is wrong, say so at the next gate with reasoning. The invariants in `CLAUDE.md` are the short form of these.

## D1. Process model
A Django management command (`run_risk_provider`) in the monolith codebase: a separate OS process and a separate Kubernetes Deployment built from the same image as the monolith.
- The Sport domain lives in the monolith, and the task requires monolith-side effects, so keeping the command in the same codebase means a direct call into domain services within one transaction, with no second contract to maintain.
- A task queue does not fit: the process needs a long-lived WebSocket connection.
- The integration touches the monolith only through a port (`BetDecisionPort`). If the sports domain is extracted later, that is an adapter swap. The extraction criteria go into the README for discussion with the team; the decision itself is not made here.
- No message broker on the critical path. A broker there would add a second at-least-once hop with its own outbox and idempotent consumer, and remove nothing the DB outbox does not already give.
- The company broker (RabbitMQ) is used only to publish domain events (bet accepted, rejected, voided), behind a publisher port. The stub publishes from `transaction.on_commit` and is explicitly best-effort: a crash between commit and publish loses the event. The production path is a transactional event outbox (an events table written in the same transaction and drained by a relay); it is listed in README "next steps", not built.

## D2. DB is the source of truth
A persisted `RiskTicket` state machine. Rule: decide, commit, then send. No outbound message goes out before the decision that justifies it is durable. The ticket table is the outbox. `TICKET` delivery is at-least-once (D11). `CONFIRM_RECOMMENDATION`, `DECLINE_RECOMMENDATION` and `REQUEST_CANCELLATION` get no application ack (A-02), so we cannot know that one arrived: they are sent once, plus a bounded re-send after a reconnect (D11); the remaining loss window is stated in the README. Revised in stage 0 (previously "delivery is at-least-once" for every message). Correctness comes from idempotency: provider-side by `ticket_id` (declared assumption A-03) and our side by compare-and-swap transitions. Without A-03 we would have to keep a second store of what the provider has seen, which is out of proportion for this task. State the assumption openly.
- Considered and rejected: sending `TICKET` at most once (commit `SENT` before sending). It removes the dependence on A-03 for the costliest message, but every bet in flight during a crash or disconnect is lost, and retransmission of unanswered requests is the normal contract for this kind of provider (A-07).
- Latency: the relay polls with a short interval (about 100-200 ms) and is also woken in-process when this process commits a `*_PENDING` transition. A ticket created by the monolith waits at most one poll interval. `LISTEN/NOTIFY` is not used: it is session-level and breaks behind a transaction pooler (E-06).

## D3. Correct regardless of replica count
Work is claimed with `SELECT ... FOR UPDATE SKIP LOCKED` in a short transaction plus lease columns (`locked_by`, `locked_until`). Row locks are never held across network I/O. Every state change is a conditional update (expected state, plus lease owner where relevant). Duplicate, late and unknown-ticket messages are ignored, logged and counted.
- `SKIP LOCKED` only protects the claim transaction itself. After it commits the row lock is gone; exclusivity comes from the claim query excluding unexpired leases, and safety from the conditional updates.
- The lease must exceed the worst-case send time plus a stall. An owner that stalls past its lease can cause a duplicate send; A-03 absorbs it.
- No FIFO guarantee: with `ORDER BY` at READ COMMITTED, claimed rows can come back out of order. Order is best-effort and nothing depends on it.

## D4. One central set of loops, not a coroutine per ticket
A coroutine per ticket would keep waiting state in memory, which is lost on restart, and after a reconnect or failover the recommendation can arrive at a process that holds no such future. Correlation by `ticket_id` must go through the DB anyway. So waiting is a DB state (`SENT` + `deadline_at`, D11).
- Tasks in one asyncio `TaskGroup`: connection and reader, appliers, relay (the only sender), sweeper (deadlines, retransmission, expired leases), health and metrics server. There is no leader keeper (D6).
- If any task fails, or returns at all, the process exits non-zero and Kubernetes restarts it. A loop that returns normally cancels nothing in a `TaskGroup`, so the supervisor treats a return as a failure. No task swallows `CancelledError`, otherwise shutdown hangs.
- Error taxonomy (stage 0): a compare-and-swap miss is a return value, not an exception. Transient errors (DB `OperationalError`, statement or lock timeout, deadlock or serialization failure, closed socket) are not retried inline: the row keeps its state and the next pass or an expired lease picks it up; the only exception is the applier, which retries a transient apply up to 2 times within the deadline. A timed-out `run_db` is `OutcomeUnknown` (D5). Permanent errors (domain rule, `IntegrityError`, undecodable frame) map to a definite outcome without retry. An unclassified exception is a bug and fails fast: the task fails and the process exits.
- Known risk of failing fast (accepted for this scope): a poison message, a bug triggered by one ticket's data, crash-loops the pod, because after each restart the retransmitted `TICKET` brings the same recommendation back and every other ticket stalls. Remedy if it happens: isolate per item (the applier or relay catches the unclassified exception for that one message or row, logs it with the traceback, counts `errors_total{kind="unexpected"}`, leaves the ticket for the sweeper to cancel at its deadline) while loop-level errors still crash. Listed in README "next steps".
- Inbound decoupling: the reader only decodes frames and puts them into a bounded queue; N appliers (N = the DB executor size) apply them through `run_db`. Concurrent messages for one ticket are safe because of the conditional updates. If the queue is full, the reader waits, which stops reading from the socket; if that lasts beyond the ping timeout, the session drops. That is the documented behavior during a DB outage: nothing can be applied anyway, and retransmission after the reconnect (D11) heals the in-flight tickets. Queue depth and apply latency are metrics.
- A single send path (the relay) means normal operation and crash recovery use the same code.

## D5. asyncio at the edge, sync Django ORM in the core
All ORM work runs in a dedicated `ThreadPoolExecutor` via one helper (`run_db`). The ORM is never called from the event loop. The sync layer does no network I/O other than the database. Do not use the default `sync_to_async(thread_sensitive=True)`: it pushes all DB calls through one thread, which serializes deadline-bound work.

Rationale (ADR-003): lifecycle reliability, not throughput. Fail-fast supervision with `TaskGroup` (a dead thread in a threaded design must be supervised by hand), cancellable network waits and graceful shutdown (a blocking `recv` in a thread cannot be cancelled), uniform timeouts on the async side, a mature async client with keepalive and reconnect, and an explicit seam. At the expected load a threaded design would perform about the same. Do not claim performance wins.

The `run_db` contract:
- Admission is bounded by a semaphore. `max_workers` limits concurrency, not admission: the executor's work queue is unbounded.
- Context variables are copied into the worker (`loop.run_in_executor` does not do it), so the log context (`ticket_id`, `connection_id`) survives.
- Each unit of work runs in its own transaction with `SET LOCAL statement_timeout`, `lock_timeout` and `idle_in_transaction_session_timeout`. `SET LOCAL` works behind a transaction pooler; startup options may not.
- Connection hygiene per unit of work (`close_old_connections` before and after, honoring `CONN_MAX_AGE`).
- Cancelling or timing out the await does not stop the thread: the transaction can still commit after the caller gave up. A timed-out `run_db` therefore means "outcome unknown", never "nothing happened". The caller never acts on the assumption that it failed; the next pass re-reads state. The async-side timeout is longer than `statement_timeout`, so normally the database aborts first and the outcome is known.
- Considered: `asyncio.to_thread` plus a semaphore. It uses the shared default executor, which other libraries also use, so the pool cannot be sized or isolated. Django's native connection pool (5.1+) is not needed for a small fixed set of worker threads.

## D6. Session exclusivity: the provider's session policy, no leader election of our own
Revised in stage 0 (previously a leader lease row; see "Considered" below).
- Correctness never depended on a single instance: claims, compare-and-swap transitions and provider idempotency (D3, A-03) make any number of instances safe. What remains is how many provider sessions are open at once, and the provider's session policy (A-05) decides that. We add no leader election, lease row or lock of our own. Do not call any part of this a lock, leader or fencing.
- Every instance connects. Under reject-new (the default assumption) a second instance gets `ALREADY_CONNECTED`, retries with jittered backoff capped low (about 2 s) and is in effect a hot standby. If the provider allows several sessions, all instances are active in parallel; this is correct because messages are scoped to the account (A-15), and a recommendation lost with a dead session is recovered at the retransmit point (D11).
- Replicas: 1 by default, RollingUpdate with `maxSurge: 1`, `maxUnavailable: 0`. The new pod becomes ready (D8: ready means "can take over") and is refused while the old pod holds the session; the old pod gets SIGTERM, drains and closes with 1001; the new pod's next attempt succeeds. Handover takes about the drain time plus the backoff cap. After an unclean death the provider keeps the dead session until it misses pings (about 30 s, A-05); the takeover waits for that whatever the replica count.
- Session-conflict policy: unknown. Transactional, session-stateful protocols (FIX acceptors, for example) usually refuse the second session (reject-new); data-stream APIs more often let the newer connection win (kick-out). Under kick-out with 1 replica, the new pod displaces the terminating old one, which is harmless. With more than one replica two pods would displace each other in a loop (slowed only by the `DISPLACED` backoff), so more than one replica is supported only under reject-new or multi-session.
- The transport classifies connection outcomes: `AUTH_FAILED` (fatal), `DISPLACED` (kicked out: close, no immediate reconnect, long backoff), `ALREADY_CONNECTED` (rejected: short capped backoff with jitter), `TRANSIENT` (reconnect with backoff; a planned close by the provider, A-14, reconnects at once). The handshake can be rejected at the HTTP upgrade or accepted and then closed with a close code; handle both. All of this happens inside the connection task: no task returns, so invariant 4 holds as written. Session status is a metric.
- Considered: a leader lease row `(name, holder, expires_at)` renewed by conditional update on DB time, with a voluntary step-down on loss. Its only benefit is preventing kick-out flapping with more than one replica; its cost is a model, a keeper loop, step-down supervision (a leadership-term `TaskGroup`) and reserved executor capacity so renewals are not starved by appliers. With 1 replica, overlap happens only during a rollout, when the old pod is terminating anyway. It stays the documented upgrade path (ADR-004) if the provider uses kick-out and more than one replica is needed. A Postgres advisory lock is rejected even for that path: it is session-level, fails behind a transaction pooler, is tied to one connection and thread (Django's connection hygiene can silently close it), and a dead holder is noticed only through TCP keepalive. `Recreate` was rejected: downtime on every deploy, and it does not prevent overlap on eviction or manual deletion.

## D7. Cancellation
In our flow `REQUEST_CANCELLATION` is sent when our own placement flow has failed: the deadline passed, applying the decision failed, or CONFIRM was rejected or late. Our side of the bet must be settled regardless of the provider's answer, because customer money cannot wait on a third party.
- Compensate durably first: in one transaction void the bet, release or refund the wallet, set the ticket to `CANCEL_PENDING`. Only then does the relay send, and retransmit if needed (A-03).
- The provider may reject a cancellation (A-02, A-09). Rejection leads to `ESCALATED`: the provider still counts exposure for a bet we voided. Reconciliation is an operational process (business question B-03). An "unknown ticket" error in reply to a cancellation counts as done (A-09).
- Considered: waiting for the provider to accept the cancellation before voiding locally. That fits a cancellation of a bet that is valid on our side; for a failed placement it keeps customer funds in limbo on a third party's answer, and the "no answer" fallback ends in voiding anyway. ADR-005 records the trade-off.
- Never act on an ambiguous outcome (a timed-out `run_db`, a commit whose result is unknown): re-read state on the next pass (D5).
- A rejected or late CONFIRM leads to compensation and cancellation. That voids a bet the customer may already have seen as accepted, which is a business decision: the default is stated as business question B-01, not presented as a provider fact.

## D8. Probes and shutdown
- Startup: settings valid, DB reachable, migrations applied (E-11).
- Liveness: every loop bumps its heartbeat on every iteration, including iterations whose DB call failed. Stale heartbeat means unhealthy. Liveness never depends on the provider or on DB health: an outage of either must not cause a restart storm, but a hung loop must cause a restart.
- Readiness means "this pod can take over the work": initialized and DB reachable. It does NOT mean "holds the session": during a rolling update the new pod could then never become ready while the old one holds the session, and the rollout would stall. No Service routes traffic to these pods; readiness only gates rollout progress and PodDisruptionBudgets. Session status is a metric.
- Probes and metrics are served by one small HTTP server on a separate port.
- SIGTERM drain, bounded: stop claiming `PENDING_SEND`; keep the reader and appliers running for `SENT` tickets until their recommendation arrives or the drain budget ends; flush `*_PENDING`; close the WebSocket with code 1001. Whatever is left is resumed through retransmission (D11) by whichever instance holds the next session. `terminationGracePeriodSeconds` exceeds the drain budget plus the WebSocket close timeout (10 s by default) plus a margin.
- The SIGTERM handler is installed before slow initialization: with an exec-form `CMD`, Python is PID 1 and ignores SIGTERM until a handler exists. Alternatively use an init process in the image.

## D9. Load assumption
Declared assumption: tens of tickets per second for the sports flow, with peaks during live events. Conservative, and not a design driver for the sync/async choice. It sizes the DB executor and therefore the connections per pod.

## D10. Configuration and secrets
- All configuration is environment variables, read once at startup into a typed, validated settings object. A missing or invalid required variable fails fast with a clear message, so the startup probe never goes green. Secrets are `SecretStr`: they never appear in logs, reprs, metrics or exception messages.
- `.env` is a developer convenience loaded by tooling (make, docker compose). Application code never reads a `.env` file, so production behavior cannot silently depend on one. `.env` is gitignored and dockerignored; `.env.example` contains throwaway placeholders only.
- Production: the platform injects values from a Kubernetes Secret (or a secret manager through the platform). Provider traffic uses `wss://` outside local development.
- Rotation: static secrets are read at startup, so rotating them is a rolling restart. The provider access token is short-lived and fetched before every connect (A-11), so it is not a static secret; the client credentials are. A secret manager is the natural next step and belongs in the README.

## D11. Deadlines and retransmission
- `deadline_at` is set per ticket when it is created, from one configured deadline (A-04: one ticket type). It counts from creation because the customer is waiting from that moment; time spent unsent (provider down) uses up the budget.
- The relay retransmits `TICKET` once if no recommendation has arrived by a retransmit point (about half the deadline), and retransmits `TICKET` for every `SENT` ticket after each (re)connect (A-07). `*_PENDING` messages are sent by the normal relay path. All of this relies on A-03.
- Final messages have no ack (A-02), so a frame written just before a disconnect may be lost. Each send records `last_sent_at`. After a reconnect the relay re-sends the final message of tickets sent within the loss window before the disconnect (ping interval plus ping timeout, about 40 s): `REQUEST_CANCELLATION` always (idempotent, no "too late", A-09); `CONFIRM_RECOMMENDATION` only while still inside the provider's confirm window (A-04), because a duplicate after it would draw a "late" `ERROR` and a false compensation; `DECLINE_RECOMMENDATION` never (a lost one leaves the ticket not accepted on the provider side anyway, A-07).
- At the deadline the sweeper compensates and moves the ticket to `CANCEL_PENDING` (D7), also for tickets still `PENDING_SEND`: one of them may have reached the provider before a crash, and a cancellation for an unknown ticket is harmless (A-09).
- A recommendation that arrives after the deadline is ignored and counted.

## D12. Time source
- Comparisons that cross pods (ticket leases, deadlines) are evaluated in SQL against DB time. `now()` is the transaction start time, which is fine because these transactions are short.
- Pure domain functions receive `now` as an argument; they never read a clock.
- The provider's `ts` is logged and used for latency metrics, never in a decision.
- Tests move time by writing `deadline_at` or `locked_until` in the past, or by passing `now`; no real sleeps.
