# Decisions D1-D13

Each decision gives its reasoning and the alternatives considered. The invariants in `CLAUDE.md` are the short form of D1-D12; D13 collects the code-level patterns. Assumption IDs (A-xx provider, B-xx business, E-xx environment) refer to `docs/PROVIDER_QUESTIONS.md`.

## D1. Process model
A Django management command (`run_risk_provider`) in the monolith codebase: a separate OS process and a separate Kubernetes Deployment built from the same image as the monolith.
- The Sport domain lives in the monolith, and the task requires monolith-side effects, so keeping the command in the same codebase means a direct call into domain services within one transaction, with no second contract to maintain.
- A task queue does not fit: the process needs a long-lived WebSocket connection.
- The integration touches the monolith only through a port (`BetDecisionPort`). If the sports domain is extracted later, that is an adapter swap. When to extract is a decision for the team, not made here.
- No message broker on the critical path. A broker there would add a second at-least-once hop with its own outbox and idempotent consumer, and remove nothing the DB outbox does not already give.
- Domain events to the company broker (RabbitMQ: bet accepted, rejected, voided) are not built: the task does not need them. The production path is a transactional event outbox (an events table written in the same transaction as the bet change, drained by a relay). Considered: a best-effort `on_commit` publisher stub; it loses events on a crash and adds nothing the task asks for.

## D2. DB is the source of truth
A persisted `RiskTicket` state machine. Rule: decide, commit, then send. No outbound message goes out before the decision that justifies it is durable. The ticket table is the outbox. `TICKET` delivery is at-least-once (D11). `CONFIRM_RECOMMENDATION`, `DECLINE_RECOMMENDATION` and `REQUEST_CANCELLATION` get no application ack (A-02), so we cannot know that one arrived: they are sent once, plus a bounded re-send after a reconnect (D11); the remaining loss window is stated in the README. Correctness comes from idempotency: provider-side by `ticket_id` (declared assumption A-03) and our side by compare-and-swap transitions. Without A-03 we would have to keep a second store of what the provider has seen, which is out of proportion here. The assumption is stated openly.
- Considered and rejected: sending `TICKET` at most once (commit `SENT` before sending). It removes the dependence on A-03 for the costliest message, but every bet in flight during a crash or disconnect is lost, and retransmission of unanswered requests is the normal contract for this kind of provider (A-07).
- Latency: the relay polls with a short interval (100 ms); a ticket waits at most one poll interval. No in-process wakeup: tickets are created by web pods in other processes, and the confirm window (A-04) is seconds long, so a wakeup saves nothing that matters. `LISTEN/NOTIFY` is not used: it is session-level and breaks behind a transaction pooler (E-06).

## D3. Correct regardless of replica count
Work is claimed with `SELECT ... FOR UPDATE SKIP LOCKED` in a short transaction plus lease columns (`locked_by`, `locked_until`). Row locks are never held across network I/O. Every state change is a conditional update (expected state, plus lease owner where relevant). Duplicate, late and unknown-ticket messages are ignored, logged and counted.
- `SKIP LOCKED` only protects the claim transaction itself. After it commits the row lock is gone; exclusivity comes from the claim query excluding unexpired leases, and safety from the conditional updates. This is not a distributed lock: an owner that stalls past its lease can cause a duplicate send, which A-03 absorbs.
- The lease must exceed the worst-case send time plus a stall. Defaults: send timeout 2 s, lease 6 s (validated to exceed the send timeout plus the `run_db` await timeout). Tickets claimed by a process that died wait out its lease against a 10 s deadline, so the lease is kept short: a longer one let a crashed batch reach its deadline and be cancelled instead of sent.
- An expired lease needs no requeue step: the claim query treats `locked_until < now()` as claimable. Every transition clears the lease, so a ticket moved on by a reply can be claimed for its next send at once.
- A relay whose session ends releases the leases of its current batch on the way out, so the next session of the same process sends the unsent rest at once instead of waiting the lease out. A claim still running when the relay is cancelled is waited out (bounded by the `run_db` await timeout) and its rows released too: the worker thread commits whatever the caller does, and without this about one session end in twenty left a batch nobody sent until the lease ran out. The release is by primary key and owner, so it needs no index. What it does not cover runs out with the lease, as after a crash: a release that fails, a claim that outlives its await timeout, a row whose `record_send` failed transiently in an earlier batch.
  - Considered: releasing every lease of the owner at session start (needs a partial index on `locked_by`, otherwise a sequential scan against a 2 s statement timeout, and still races with a claim that commits late); tracking claimed ids in memory (the same with more state); releasing only in the indexed outbox states (misses final re-sends).
- No FIFO guarantee: with `ORDER BY` at READ COMMITTED, claimed rows can come back out of order. Order is best-effort and nothing depends on it.

## D4. One central set of loops, not a coroutine per ticket
A coroutine per ticket would keep waiting state in memory, which is lost on restart, and after a reconnect or failover the recommendation can arrive at a process that holds no such future. Correlation by `ticket_id` must go through the DB anyway. So waiting is a DB state (`SENT` + `deadline_at`, D11).
- Tasks in one top-level asyncio `TaskGroup`: the connection task, N appliers, the sweeper (deadlines). The health and metrics server is not a task: it is opened around the startup check and the group, because it must answer before any loop runs and aiohttp runs no loop of ours to supervise; a failed bind fails the start.
- The connection task runs one nested group per session: the reader, the relay (the only sender, including retransmission) and a watch on the socket. The relay lives only as long as its session, so the re-send owed after a (re)connect is simply how every session starts, and no task holds a shared "current socket". A closed socket ends the session group with `SessionEnded` and the connection task connects again (D6); any other error in it ends the process. Considered: a permanent relay that waits on a session handle and a reconnect event; more shared state, same behaviour.
- If any task fails, or returns at all, the process exits non-zero and Kubernetes restarts it. A loop that returns normally cancels nothing in a `TaskGroup`, so the supervisor treats a return as a failure. No task swallows `CancelledError`, otherwise shutdown hangs.
- Error taxonomy: a compare-and-swap miss is a return value, not an exception. Transient errors (DB `OperationalError`, statement or lock timeout, deadlock or serialization failure, closed socket) are not retried inline: the row keeps its state and the next pass or an expired lease picks it up. That includes the applier: a transient apply failure leaves the ticket `SENT`, and the retransmit point brings the recommendation back (A-03), so there is one recovery path, not two. A timed-out `run_db` is `OutcomeUnknown` (D5). Permanent errors (domain rule, `IntegrityError`, undecodable frame) map to a definite outcome without retry. An unclassified exception is a bug: within one message or one ticket it is contained to that item (below); anywhere else it fails the task and the process exits.
- One exception to no inline retry: recording a refused confirm or cancellation (`ESCALATED`) is retried in place, 3 attempts 0.5 s apart, on transient DB errors only. The provider does not repeat an error, so no retransmission brings it back. A repeat is safe because the transition is conditional; after an unknown outcome a miss may be the earlier attempt that committed, and it is counted as a late error. When every attempt fails the refusal is lost (error log, `risk_escalation_failures_total`) unless a re-send after a reconnect draws the same error again. Considered: an inbox table for inbound errors; it does not help during a real DB outage, because the insert fails too.
- Sweeper starvation: the sweeper takes expired tickets oldest first, so a full batch of tickets whose compensation keeps failing (an accepted bet behind a waiting ticket, a lock held by the monolith) would hold back every ticket behind it. A ticket whose compensation failed is left out of the sweeper's batches for `RISK_SWEEPER_RETRY_FAILED_AFTER` (5 s). The skip lives in memory: a restart forgets it and retries every failed ticket at once, which is harmless.
- Applying a recommendation has three failure classes (`TICKET_LIFECYCLE.md`, rows 6-8): a domain rejection is a decline (`DECLINE_PENDING`); a transient failure or an unknown outcome leaves the ticket `SENT` (retransmission, then the deadline); a recognized permanent technical failure compensates and cancels (`CANCEL_PENDING`, reason `APPLY_FAILED`). The last is the "unexpected effects in our system" path.
- Per-item isolation, loop-level fail-fast. An applier handling one message and the sweeper compensating one ticket catch any unclassified exception for that item, log it at error level with the traceback, the message type and `ticket_id`, count it in `risk_unexpected_errors_total{loop}` (`applier`, `sweeper`), and carry on. The unit of work rolled back, so no money moved: a ticket whose recommendation hit the bug stays waiting, the retransmission brings the recommendation back once, and otherwise the deadline cancels it; a ticket whose compensation hit it is skipped like a failed compensation and retried every `RISK_SWEEPER_RETRY_FAILED_AFTER`, so it keeps alerting until a person resolves it. Everything outside one item (the session, the reader, the relay, the supervisor, the sweeper's claim query) still fails the task and ends the process. `LockedTransitionMissed` (a transition that missed under the ticket lock) is raised inside one unit of work and is isolated like any other unclassified error. Why: failing fast on a bug triggered by one ticket's data crash-looped the pod, because after each restart the retransmitted `TICKET` brought the same recommendation back, and an expired ticket whose compensation hit the bug was found again within a second of every start, forever, while every other ticket stalled. Trade-off: a bug now shows as a metric, not a crash, so the alert is on any increase of `risk_unexpected_errors_total`; a bug that hits every item (in `run_db` itself, say) keeps the pod live and failing each message instead of restarting it. Considered: keeping fail-fast and relying on Kubernetes' restart backoff (every other ticket still stalls, and the compensation crash-loop never ends); a dead-letter table (nothing to replay: the retransmission or the sweeper already brings the item back).
- Inbound decoupling: the reader only decodes frames and puts them into a bounded queue; N appliers apply them through `run_db`. The DB executor has one worker per applier plus one each for the relay and the sweeper, so a burst of applies cannot starve sending or deadlines. Concurrent messages for one ticket are safe because of the ticket lock and the conditional updates. If the queue is full, the reader waits, which stops reading from the socket; if that lasts beyond the ping timeout, the session drops. That is the intended behaviour during a DB outage: nothing can be applied anyway, and retransmission after the reconnect (D11) heals the in-flight tickets. Queue depth is a metric, and a session that ends with a full queue is labelled so.
- A single send path (the relay) means normal operation and crash recovery use the same code.

## D5. asyncio at the edge, sync Django ORM in the core
All ORM work runs in a dedicated `ThreadPoolExecutor` via one helper (`run_db`). The ORM is never called from the event loop. The sync layer does no network I/O other than the database. The default `sync_to_async(thread_sensitive=True)` is not used: it pushes all DB calls through one thread, which serializes deadline-bound work.

Rationale: lifecycle reliability, not throughput. Fail-fast supervision with `TaskGroup` (a dead thread in a threaded design must be supervised by hand), cancellable network waits and graceful shutdown (a blocking `recv` in a thread cannot be cancelled), uniform timeouts on the async side, a mature async client with keepalive, and an explicit seam. At the expected load a threaded design would perform about the same; no performance win is claimed.

The `run_db` contract:
- Admission is bounded by a semaphore. `max_workers` limits concurrency, not admission: the executor's work queue is unbounded. A permit is released when the worker thread finishes, not when the awaiting coroutine times out; otherwise more threads than permits would be busy.
- The wait for admission is bounded: no permit within the admission timeout raises `NotAdmitted`. Unlike `OutcomeUnknown` its outcome is known (the work never ran), so it is transient and needs no re-read.
- Context variables are copied into the worker (`loop.run_in_executor` does not do it), so the log context (`ticket_id`, `connection_id`) survives.
- Each unit of work runs in its own transaction with `SET LOCAL statement_timeout`, `lock_timeout` and `idle_in_transaction_session_timeout`. `SET LOCAL` works behind a transaction pooler; startup options may not.
- Connection hygiene per unit of work (`close_old_connections` before and after, honouring `CONN_MAX_AGE`). `CONN_MAX_AGE` comes from the environment per Deployment: the integration's thread pool is fixed, so persistent connections give exactly that many steady connections. The default stays Django's 0 because the settings module is shared with the web pods, whose connection behaviour is not the integration's to change; the integration Deployment sets about 60 s (connections also rotate after a failover), and the command warns at startup when it is 0. Correctness does not depend on it, only latency and connection churn.
- `CONN_HEALTH_CHECKS`: one `SELECT 1` per unit replaces a connection that died while idle (database restart, failover, pooler restart, NAT idle timeout), instead of failing one unit per worker thread after every failover.
- `connect_timeout` defaults to 2 s, the minimum psycopg honours. Without it psycopg waits 130 s on an unreachable host, the worker thread keeps its permit, and a few such units take every permit. It stays below the await timeout, so a failed connect is a transient `OperationalError`, not an unknown outcome. A value in `DATABASE_URL` wins.
- Cancelling or timing out the await does not stop the thread: the transaction can still commit after the caller gave up. A timed-out `run_db` therefore means "outcome unknown", never "nothing happened". The caller never acts on the assumption that it failed; the next pass re-reads state. The await timeout is longer than `statement_timeout`, so normally the database aborts first and the outcome is known.
- Considered: `asyncio.to_thread` plus a semaphore (it uses the shared default executor, which other libraries also use, so the pool cannot be sized or isolated); Django's native connection pool (one persistent connection per fixed worker thread already is a pool of that size, the native pool needs `psycopg-pool`, and behind a transaction pooler it would pool twice).

## D6. Session exclusivity: the provider's session policy, no leader election of our own
- Correctness never depends on a single instance: claims, compare-and-swap transitions and provider idempotency (D3, A-03) make any number of instances safe. What remains is how many provider sessions are open at once, and the provider's session policy (A-05) decides that. We add no leader election, lease row or lock of our own, and nothing here is called a lock, leader or fencing.
- Every instance connects. Under reject-new (the default assumption) a second instance is refused (`ALREADY_CONNECTED`), retries with a short jittered delay that does not grow (about 2 s) and is in effect a hot standby. If the provider allows several sessions, all instances are active in parallel; this is correct because messages are scoped to the account (A-15), and a recommendation lost with a dead session is recovered at the retransmit point (D11).
- Replicas: 1 by default, RollingUpdate with `maxSurge: 1`, `maxUnavailable: 0`. The new pod becomes ready (D8: ready means "can take over") and is refused while the old pod holds the session; the old pod gets SIGTERM, drains and closes with 1001; the new pod's next attempt succeeds. Handover takes about the drain time plus the standby retry. After an unclean death the provider keeps the dead session until it misses pings (about 30 s, A-05); the takeover waits for that whatever the replica count.
- Session-conflict policy: unknown. Transactional, session-stateful protocols (FIX acceptors, for example) usually refuse the second session (reject-new); data-stream APIs more often let the newer connection win (kick-out). Under kick-out with 1 replica, the new pod displaces the terminating old one, which is harmless. With more than one replica two pods would displace each other in a loop (slowed only by the `DISPLACED` backoff), so more than one replica is supported only under reject-new or multi-session.
- Reconnect delay per outcome (`runtime/backoff.py`, all configurable), every delay jittered down by up to half, never to zero:
  - `TRANSIENT`: 0.5 s doubling to 5 s. The cap stays under the ticket deadline, and the command refuses to start otherwise: bets placed while no session is open are voided at their deadline, so a longer delay only adds voided bets, and with one connection per pod a short cap puts no real load on the provider. Considered: a 30 s cap, the usual default.
  - Planned close by the provider (A-14): at once if the session was stable, otherwise like a transient failure, so a provider that closes with the planned code right after the handshake cannot cause a tight loop.
  - `ALREADY_CONNECTED`: 2 s, never growing, so a standby takes over soon after the holder leaves.
  - `DISPLACED`: 60 s.
  - `AUTH_FAILED`: 30 s doubling to 5 min, logged at error level and counted for an alert. Considered: exiting the process; an auth outage on the provider's side would then crash-loop every pod.
  - Endings with the same outcome in a row form a streak that grows the delay; a session that stayed open for 60 s, or a different outcome, starts a new one. A handshake alone does not reset it, and a standby that finally takes over does not carry a streak of hundreds of refusals into its first real drop.
- The token is fetched before every connect with a timeout (5 s); a timeout is transient. The handshake can be rejected at the HTTP upgrade or accepted and then closed with a close code; both are classified and tested. All of this happens inside the connection task: no task returns, so the supervision rule of D4 holds as written. `risk_session_open` (gauge) and `risk_sessions_ended_total` (by outcome, and whether the inbound queue was full when the session dropped) are the session metrics.
- Considered: a leader lease row `(name, holder, expires_at)` renewed by conditional update on DB time, with a voluntary step-down on loss. Its only benefit is preventing kick-out flapping with more than one replica; its cost is a model, a keeper loop, step-down supervision and reserved executor capacity so renewals are not starved by appliers. With 1 replica, overlap happens only during a rollout, when the old pod is terminating anyway. It stays the documented upgrade path if the provider uses kick-out and more than one replica is needed. A Postgres advisory lock is rejected even for that path: it is session-level, fails behind a transaction pooler, is tied to one connection and thread (Django's connection hygiene can silently close it), and a dead holder is noticed only through TCP keepalive. `Recreate` is rejected: downtime on every deploy, and it does not prevent overlap on eviction or manual deletion.

## D7. Cancellation
`REQUEST_CANCELLATION` is sent when our own placement flow has failed: the deadline passed, applying the decision failed with a recognized permanent technical error, or the provider refused the `TICKET`. Our side of the bet must be settled regardless of the provider's answer, because customer money cannot wait on a third party.
- Compensate durably first: in one transaction void the bet, release the held stake, set the ticket to `CANCEL_PENDING`. Only then does the relay send, and re-send after a reconnect if needed (D11). Compensation happens only from the pre-acceptance states (`PENDING_SEND`, `SENT`), where the stake is held and never captured, so no path refunds a captured stake.
- Compensation is idempotent: a bet already voided or rejected, and a stake already released or never held, count as compensated, so an `APPLY_FAILED` cancellation completes even when the failed apply found the hold missing. An accepted bet or a captured stake is refused (`PermanentApplyError`) and the ticket stays as it is.
- The provider may refuse a cancellation (A-02, A-09). A refusal leads to `ESCALATED`: the provider still counts exposure for a bet we voided. Reconciliation is an operational process (B-03). An "unknown ticket" error in reply to a cancellation counts as done (A-09).
- Considered: waiting for the provider to accept the cancellation before voiding locally. That fits a cancellation of a bet that is valid on our side; for a failed placement it keeps customer funds in limbo on a third party's answer, and the "no answer" fallback ends in voiding anyway.
- Never act on an ambiguous outcome (a timed-out `run_db`, a commit whose result is unknown): re-read state on the next pass (D5).
- A refused or late confirm leads to `ESCALATED`, with no automatic void or refund (B-01). The bet is accepted on our side and the customer may have seen it; reversing it on an ambiguous third-party signal is worse than an exposure mismatch that risk operations resolve. It is a business decision, stated as B-01, not presented as a provider fact. Considered: voiding automatically, which needs a refund path from an accepted state. Manual resolution of `ESCALATED` tickets is a next step.

## D8. Probes and shutdown
- Startup: settings valid, DB reachable, migrations applied (E-11). Invalid settings end the command before anything starts. Otherwise the probe server starts first and the app checks the database and the migration plan through `run_db` every 2 s; no loop runs until both pass.
- Liveness: every loop bumps its heartbeat on every iteration, including iterations whose DB call failed. Liveness never depends on the provider or on DB health: an outage of either must not cause a restart storm, but a hung loop must cause a restart.
  - Each beat sets a deadline: now plus `RISK_LIVENESS_STALE_AFTER` (60 s) plus the loop's planned wait (a reconnect delay, a sweeper interval). Liveness fails once any deadline has passed.
  - A loop parks while it waits on something that may legitimately last forever: an applier on an empty queue, the connection task while a session is open (that session's relay beats instead). A parked loop has no deadline until it beats again. The reader has no heartbeat: it waits on the socket, and the keepalive covers a dead connection.
  - Batch loops beat per item, so the longest normal gap is one unit of work, or an escalation retried on a slow database (about 25 s).
  - Considered: bounded waits everywhere (more wake-ups, and they cannot cover an open session); an event-loop lag watchdog only (misses a coroutine stuck in an await).
- Readiness means "this pod can take over the work": started, not draining, DB reachable. It does not mean "holds the session": during a rolling update the new pod could then never become ready while the old one holds the session, and the rollout would stall. No Service routes traffic to these pods; readiness only gates rollout progress. Session status is a metric.
  - "DB reachable" is passive: a unit of work committed within `RISK_READINESS_DB_WITHIN` (10 s). The sweeper commits one every second, standby or not, so this costs nothing and a probe never takes a `run_db` permit. Considered: `SELECT 1` through `run_db` per probe, which competes for permits sized for the loops and flaps with `NotAdmitted` under load.
- Probes and metrics are served by one small HTTP server on a separate port (`/startupz`, `/livez`, `/readyz`, `/metrics`, 9100).
- SIGTERM drain, bounded: stop claiming `PENDING_SEND`; stop the reader; let the appliers finish the queue; flush `*_PENDING` once; close the WebSocket with 1001. The drain does not wait for recommendations of `SENT` tickets: retransmission (D11) by whichever instance holds the next session recovers them, and the drain time stays predictable.
  - The connection task runs the drain, because it owns the session. A stop task in the session group ends it, which cancels the reader and the relay; the relay releases its batch's leases. Then `queue.join()`, one pass of `Relay.flush` over `CONFIRM_PENDING`, `DECLINE_PENDING` and `CANCEL_PENDING`, and the close with 1001. Then `Drained` ends the process with code 0. Considered: a separate coordinator task, which would need a shared handle on the current session (rejected for the same reason in D4).
  - The queue join and the flush share `RISK_DRAIN_TIMEOUT` (10 s); whatever is left is owed in the database and goes out on the next session. Without an open session, or during startup, a shutdown request exits at once, also from inside a reconnect delay. The sweeper runs until the end: harmless, and its cancellations are durable.
  - `RISK_WS_CLOSE_TIMEOUT` is 2 s: it bounds the close, and after a keepalive failure it is also how long the library waits for a close handshake that an unread socket never completes before the session counts as ended.
  - `terminationGracePeriodSeconds: 30` exceeds the drain (10 s), the close (2 s) and the units of work finishing (`RISK_DB_AWAIT_TIMEOUT`, 3 s) plus a margin.
- The SIGTERM handler is installed before slow initialization: with an exec-form `CMD`, Python is PID 1 and ignores SIGTERM until a handler exists. The command installs the event loop's handler before the app's slow start (waiting for the database and migrations). The window left is Django's setup and the settings validation, a fraction of a second in which a SIGTERM is ignored and the kubelet kills the pod at the grace period with nothing running. Considered: a plain handler earlier in the command (covers milliseconds of that window, not Django's setup); an init process such as tini in the image (one more binary, for that window only).
- Kubernetes wiring is documented here, not shipped. The task asks for a Kubernetes-friendly process; the interface is the probes, the SIGTERM behaviour, configuration from the environment and JSON logs on stdout, all in code and tested. A manifest in the repository would be validated by nothing and full of placeholders, and the platform owns its manifests.
  - `startupProbe` on `/startupz`: period 2 s, failure threshold 90 (3 minutes for the database and migrations).
  - `livenessProbe` on `/livez`: period 10 s, failure threshold 3.
  - `readinessProbe` on `/readyz`: period 5 s; gates the rollout, routes no traffic. No Service, no PodDisruptionBudget (with one replica it blocks node drains).
  - `terminationGracePeriodSeconds: 30`; `replicas: 1`, RollingUpdate `maxSurge: 1`, `maxUnavailable: 0` (D6).
  - Only this Deployment sets `DATABASE_CONN_MAX_AGE=60`. `DJANGO_SECRET_KEY`, `DATABASE_URL` and `RISK_PROVIDER_TOKEN` come from a Secret. Resources unmeasured: about 100m CPU and 256Mi requested, a 512Mi memory limit, no CPU limit.
- Metrics are in-process and labelled by bounded enums only. Not built: database-wide backlog gauges (unresolved tickets by state, age of the oldest). Every pod would report the same database-wide numbers and need a loop of its own, for failures the session, error and escalation metrics already signal. The production path is a SQL exporter running the two queries against the partial indexes, outside the integration.
- Alerts (described, not shipped): `risk_sessions_ended_total{outcome="auth_failed"}` increasing; `max(risk_session_open) == 0` for some minutes across pods; `risk_sessions_ended_total{inbound_queue_full="true"}` increasing (appliers behind the provider); `risk_compensation_failures_total` increasing (the sweeper cannot cancel); `risk_escalations_total` or `risk_escalation_failures_total` increasing.

## D9. Load assumption
Declared assumption: tens of tickets per second for the sports flow, with peaks during live events. Conservative, and not a design driver for the sync/async choice. It sizes the DB executor and therefore the connections per pod.

## D10. Configuration and secrets
- All configuration is environment variables, read once at startup into a typed, validated settings object. A missing or invalid required variable fails fast with a clear message, so the startup probe never goes green. Secrets are `SecretStr`: they never appear in logs, reprs, metrics or exception messages. The websockets library logs request headers at DEBUG, so its logger is pinned at INFO to keep the bearer token out.
- `.env` is a developer convenience loaded by tooling (make, docker compose). Application code never reads a `.env` file, so production behaviour cannot silently depend on one. `.env` is gitignored and dockerignored; `.env.example` contains throwaway placeholders only.
- Production: the platform injects values from a Kubernetes Secret (or a secret manager through the platform). Provider traffic uses `wss://`; `ws://` needs an explicit flag for local development.
- Rotation: static secrets are read at startup, so rotating them is a rolling restart. The provider access token is short-lived and fetched before every connect (A-11), so it is not a static secret; the client credentials are. A secret manager is a next step.

## D11. Deadlines and retransmission
- `deadline_at` is set per ticket when it is created, from one configured deadline (A-04: one ticket type). It counts from creation because the customer is waiting from that moment; time spent unsent (provider down) uses up the budget.
- The relay retransmits `TICKET` once if no recommendation has arrived by a retransmit point (half the deadline), and retransmits `TICKET` for every `SENT` ticket after each (re)connect (A-07). `*_PENDING` messages are sent by the normal relay path. All of this relies on A-03.
- Final messages have no ack (A-02), so a frame written just before a disconnect may be lost. Each send records `last_sent_at`. After a reconnect the relay re-sends the final message of every closed ticket (`CONFIRMED`, `DECLINED`, `CANCELLED`) sent within the loss window before the disconnect (ping interval plus ping timeout, 40 s), whatever its type.
  - The window ends at the latest final send in the table, not at the disconnect: a new process does not know when its predecessor's session died, and no final goes out between two sessions, so this end lies at or after the real one and the window covers everything a dead connection can lose, however long the restart took. Considered: ending it at the connect, which misses those frames whenever the restart took longer than the window. With several active sessions another instance's sends can move that end later than this instance's disconnect; that narrow gap exists only in the multi-session case.
  - It is safe because a duplicate is a no-op (A-03), including a duplicate confirm after the confirm window. If the original confirm was really lost and the re-send comes too late, the provider's `ERROR` leads to `ESCALATED`, not to a void (B-01), which is the right outcome for a confirm the provider never took.
  - Each final message is re-sent after one reconnect at most (`final_resends`). A re-send records `last_sent_at` like any send, which puts it inside the next session's window; without the cap, frequent reconnects would re-send the same finals again and again, a set that only grows, and a provider that refused duplicates would escalate tickets that finished correctly. Lost with the cap: a re-send that dies with a second session inside the loss window. Considered: capping by the age of the first final send, which loses the property that a restart of any length re-sends what its predecessor may have lost.
- At the deadline the sweeper compensates and moves the ticket to `CANCEL_PENDING` (D7), also for tickets still `PENDING_SEND`: one of them may have reached the provider before a crash, and a cancellation for an unknown ticket is harmless (A-09).
- The deadline is a hard line on DB time: a recommendation applied at or after `deadline_at` is ignored and counted (`reason="past_deadline"`), and the ticket is left for the sweeper to cancel. The applier and the sweeper read the deadline under the same ticket lock, so exactly one of them acts. Considered: applying a recommendation that arrives after the deadline but before the sweeper's pass, a window that looks like one sweeper interval. A database stall stretches it to the length of the stall, and on recovery the queued recommendations reach the lock before the sweeper and accept bets long after the deadline; a confirm that late would likely miss the provider's confirm window (A-04) and escalate a bet whose stake is already captured (B-01). Cost of the hard line: a recommendation that misses the deadline by milliseconds voids a bet that could have been accepted.

## D12. Time source
- Comparisons that cross pods (ticket leases, deadlines) are evaluated in SQL against DB time. Queries use Django's `Now()`, which is `statement_timestamp()` on PostgreSQL, and raw SQL uses the same clock (`db_now`); the transactions are short, so the gap to the transaction start does not matter.
- The domain has no time input at all: it never reads a clock, and every deadline or lease comparison happens in SQL.
- The provider's `ts` is logged only, never used in a decision.
- Tests move time by writing `deadline_at`, `retransmit_at` or `locked_until` into the past on DB time; no real sleeps.

## D13. Code-level patterns
- Layering, enforced by import-linter: `domain` imports the standard library only; `protocol` imports pydantic only and is the anti-corruption layer for every wire-format guess; `persistence` and `models.py` are the only ORM users; `runtime` and `transport` are async and import neither Django nor the models directly (`allow_indirect_imports`, with Django's `SynchronousOnlyOperation` as the runtime guard). This keeps one layout without a port per DB call.
- Ports only at real seams: the monolith (`BetDecisionPort`) and the provider token (`TokenProvider`). No generic repository over the ORM, no DI framework: manual wiring in one composition root (`runtime/app.py`). DDD-lite: `RiskTicket` is the aggregate and changes state only through the transition table in `domain/machine.py`.
- Persistence: purpose-named module functions, no repository classes. `run_db` (a `DbRunner` built by the composition root, one set of timeouts) owns the unit of work: hygiene, `atomic`, `SET LOCAL` timeouts. Monolith services keep their own `atomic`: called in the monolith it is the transaction; called through the adapter it is a savepoint of the `run_db` unit, and an exception rolls the whole unit back.
- Money-moving transitions use one pattern: lock, decide, transition, in one unit of work. `lock_awaiting` takes `SELECT ... FOR UPDATE` on the ticket in its source states and reads whether its deadline has passed (no row: duplicate or late; past the deadline: left to the sweeper, D11); the port decides and applies; the conditional transition then cannot miss under the lock (a miss raises `LockedTransitionMissed`, a bug). The target of an ACCEPT depends on the monolith's answer, and the limit check and the capture stay one port call. A duplicate or a racing cancellation waits for the lock and then finds nothing to do. Considered: a conditional update first with a read-only check (two patterns, check and capture not atomic); update first with a savepoint rollback on rejection (control flow through exceptions).
- The port runs inside the integration's transaction and under the ticket lock, so it does database work only: no network I/O, no waiting. A monolith operation that needs a remote call would need a saga (record intent, commit, call, record outcome). Lock order everywhere: ticket, bet, hold, wallet; `place_bet` inserts a new ticket and never waits on an existing one.
- Apply-failure classes: permanent means `IntegrityError`, `DataError` or `PermanentApplyError` (the adapter's translation of a broken monolith invariant); transient means `OperationalError`, `InterfaceError`, `OutcomeUnknown` or `NotAdmitted`; everything else, `ProgrammingError` included, is unclassified and propagates to the loop, which contains it to that one item and counts it (D4), so a cancellation never hides a bug (`persistence/errors.py`).
- Coupling between `betting` and `risk_integration`: one entry point per direction. `place_bet` calls only `risk_integration.api.enqueue_ticket` inside its own transaction; the integration reaches the monolith only through `adapters/monolith.py`. Considered: a signal that creates the ticket (business flow in signals) and a third coordinating module (nothing gained at this size). On extraction the api call becomes an outbox event and the adapter a client.
- Ticket data: `ticket_id` is a UUID we generate, separate from the bet's key; `bet_id` is a plain unique column with no foreign key (no migration dependency on `betting`); the `TICKET` payload is snapshotted into typed columns (exact money, identical retransmissions, types checked by the database), not JSON.
- Settings: the ticket deadline is a Django setting (`RISK_TICKET_DEADLINE_SECONDS`), because the web pods create tickets; the integration's own settings are `pydantic-settings` with the `RISK_` prefix and no `env_file`, validated when the command starts, so web pods need no provider variables.
- The applier queue carries decoded messages; decode errors are counted in the reader.
- Code comments state a non-obvious decision or trade-off in plain words and carry no decision or assumption IDs; a reader must not need these documents to understand a comment. Provider guesses are marked `# ASSUMPTION:` so they can be found with grep.
- Testing: pure unit tests for the domain and the codec; persistence on a real PostgreSQL (`transaction=True` where threads are involved), with real threads for races; one fake provider in-process with a few knobs; scenario tests in pytest; one test of the command as a real process (signal handler and JSON logs together). No mocked sockets, no property-based tests. While building, each invariant was also sabotaged in the code to check that a test fails; that script is not part of the deliverable.
