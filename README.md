# Интеграция с риск-провайдером по WebSocket

Интеграция это отдельный долгоживущий процесс в кодовой базе монолита: Django management command `run_risk_provider`, которая разворачивается отдельным Deployment из того же образа. Процесс держит WebSocket-сессию с провайдером, отправляет ему новые ставки, применяет рекомендации в монолите и сообщает провайдеру итог.

## Запуск

Нужны Docker и uv.

```bash
cp .env.example .env
make install
make db-up                 # PostgreSQL в docker
make check                 # ruff, mypy, import-контракты, pytest
make up                    # весь стек: Postgres, миграции, фейковый провайдер, интеграция
make demo                  # отправка 5 ставок
docker compose logs -f app
curl -s localhost:9100/readyz
curl -s localhost:9100/metrics
docker compose stop app    # SIGTERM
make down
```

Что должно получиться:
- в логах `app` (JSON) после старта `session_opened`, после `make demo` пять записей `recommendation_applied` с `ticket_id`, `decision: ACCEPT` и `state: CONFIRM_PENDING`;
- `/readyz` отвечает 200; в `/metrics` `risk_messages_sent_total` с `attempt="first"` равен 5 для `TICKET` и для `CONFIRM_RECOMMENDATION`, `risk_decisions_total{state="CONFIRM_PENDING"}` равен 5, `risk_session_open` равен 1;
- после `docker compose stop app` в логах `shutdown_requested`, `drain_started`, `drain_finished`, `integration_stopped`, а `docker compose ps -a app` показывает `Exited (0)`.

Ответ фейкового провайдера задаётся переменной `FAKE_PROVIDER_REPLY` при `make up`: `ACCEPT` (по умолчанию), `DECLINE`, `SILENT` (ставки отменяются по сроку через 10 с) или `REFUSE` (провайдер отвергает тикет).

Сценарии отказов (молчание провайдера, дубликаты и поздние сообщения, ошибки в ответ, обрыв сессии, рестарт с уже отправленными тикетами, остановка по SIGTERM) проверяются тестами против фейкового провайдера: `uv run pytest tests/test_runtime_scenarios.py tests/test_runtime_shutdown.py`.

## Архитектура

- **Таблица тикетов в базе монолита** это и состояние каждой ставки у провайдера, и outbox исходящих сообщений. Монолит создаёт тикет в той же транзакции, что и ставку.
- **Асинхронный процесс** (asyncio) держит сессию и запускает несколько циклов: отправка тикетов и ответов, приём сообщений провайдера, отмена по сроку. Синхронный Django ORM работает только в отдельном пуле потоков, никогда в event loop.
- **Монолит доступен интеграции только через порт `BetDecisionPort`** (принять, отклонить или аннулировать ставку вместе с деньгами в кошельке). Монолит, в свою очередь, видит у интеграции одну функцию `enqueue_ticket`.

Почему так: монолит уже владеет ставками и кошельками, а решение провайдера должно менять их атомарно вместе с состоянием тикета. Процесс в той же кодовой базе и той же базе данных делает это одной локальной транзакцией, без второго сервиса, второго контракта и распределённой согласованности.

Цена внедрения: один дополнительный Deployment в Kubernetes из уже существующего образа и одна таблица в существующей базе. Новой инфраструктуры нет. Рассмотренные альтернативы:

- **отдельный сервис** требует собственных репозитория, пайплайна, базы и API-контракта с монолитом, а изменение ставки, денег и тикета превращается из одной транзакции в сагу;
- **очередь задач или консьюмер брокера** не держат WebSocket-сессию, так что процесс для неё нужен всё равно, а брокер между монолитом и интеграцией добавляет ещё одно звено at-least-once: outbox на стороне монолита и идемпотентный consumer.

Порт `BetDecisionPort` оставляет вынос в отдельный сервис дешёвым: меняется адаптер, а вызов `enqueue_ticket` становится событием.

## Жизненный цикл ставки

1. Монолит создаёт ставку, блокирует её сумму в кошельке и создаёт тикет, всё в одной транзакции.
2. Интеграция отправляет тикет провайдеру. Ожидание ответа хранится в базе (тикет отправлен, срок ответа), поэтому рестарт процесса ничего не теряет. Без ответа тикет отправляется повторно на середине срока и после каждого переподключения.
3. Рекомендация применяется одной транзакцией: ставка принимается или отклоняется, сумма списывается или возвращается, тикет фиксирует ответ, который нужно отправить провайдеру.
4. Ответ провайдеру уходит только после коммита решения.
5. Если срок истёк, провайдер отверг тикет или решение не удалось применить, ставка аннулируется и сумма возвращается. Запрос на отмену уходит провайдеру после этого.
6. Если провайдер отверг подтверждение или отмену, тикет уходит на ручной разбор, ставка не меняется.

## Как читать код

Пути от `apps/risk_integration/`:

1. `runtime/app.py`: сборка зависимостей, ожидание базы и миграций, запуск циклов в одном `TaskGroup`.
2. `runtime/connection.py`: сессия с провайдером, переподключение, остановка по SIGTERM.
3. `runtime/inbound.py`: приём сообщений провайдера, очередь и обработчики.
4. `runtime/relay.py` и `runtime/sweeper.py`: отправка, повторная отправка, отмена по сроку.
5. `services.py` и `persistence/tickets.py`: применение решения (блокировка тикета, решение монолита, переход), захват тикетов и условные переходы.
6. `persistence/db.py`: раннер ORM (пул потоков, таймауты, неизвестный исход).
7. `adapters/monolith.py`: применение решения к ставке и кошельку.
8. `protocol/`: формат сообщений; здесь же собраны допущения о провайдере.

## Что настоящее, а что заглушка

- **Настоящее:** таблица тикетов и условные переходы состояний, захват на отправку с lease, раннер ORM, циклы процесса, формат сообщений и их кодирование, переподключение с классификацией причин закрытия, повторная отправка, отмена по сроку с компенсацией, пробы, метрики, остановка по SIGTERM.
- **Заглушки:** модели ставки и кошелька (минимум, нужный для транзакций), получение токена (статический токен из окружения вместо запроса к auth-эндпоинту), фейковый провайдер для тестов и демо.



## Ключевые решения

- **Процесс внутри кодовой базы монолита.** Обоснование и альтернативы в разделе [Архитектура](#архитектура).
- **База источник истины, таблица тикетов это outbox.** Сначала решение коммитится, потом отправляется сообщение.
- **Семантика доставки.** `TICKET` доставляется at-least-once. Корректность обеспечивают дедупликация на стороне провайдера по `ticket_id` (допущение) и условные переходы тикета: каждое изменение это UPDATE «из ожидаемого состояния в новое», поэтому дубликаты и поздние сообщения ничего не меняют. Альтернатива «отправлять не больше одного раза» теряла бы все ставки в полёте при сбое. `CONFIRM`, `DECLINE` и `CANCEL` доставляются без подтверждения получения и повторяются один раз после переподключения; это best-effort (см. [Известные пробелы](#известные-пробелы)).
- **Захват тикета на отправку.** Один и тот же неотправленный тикет видят несколько процессов (например, старый и новый под во время деплоя) и несколько итераций одного процесса. Отправитель берёт пачку строк через `SELECT ... FOR UPDATE SKIP LOCKED` и записывает в них lease (владелец и срок), коммитит и только потом отправляет. Так блокировка строки не держится во время сетевого вызова, другие процессы пропускают захваченные строки, а строки упавшего процесса снова становятся доступны, когда истекает lease. Это не распределённая блокировка: процесс, зависший дольше lease, может отправить сообщение дважды, и это покрывает дедупликация у провайдера.
- **asyncio на границе, синхронный ORM в пуле потоков.** Причина не в производительности: при такой нагрузке потоки работали бы так же. Причина в управлении жизненным циклом: надзор за циклами через `TaskGroup`, отменяемое ожидание сети, предсказуемая остановка по SIGTERM, единые таймауты. Полностью синхронный вариант (поток-читатель и цикл опроса) был бы равноценен по корректности.
- **Один набор циклов, а не корутина на тикет.** Сессия (чтение, отправка, наблюдение за сокетом), обработчики входящих сообщений и цикл сроков работают в одном `TaskGroup`. Упавший цикл завершает процесс, Kubernetes его перезапускает, а состояние восстанавливается из базы.
- **Свой раннер для ORM вместо `sync_to_async`.** Раннер даёт управление тем, как синхронная работа с базой встраивается в asyncio: размер пула под конкретные циклы (поток на каждый обработчик плюс отдельные для отправки и сроков, чтобы всплеск входящих не блокировал отправку), ограничение очереди на вход, таймауты `SET LOCAL` и транзакция на каждый вызов. Вызов, не дождавшийся ответа, считается вызовом с неизвестным исходом, и состояние перечитывается.
- **Собственного выбора лидера нет.** Deployment с одной репликой; во время rolling update подов ненадолго два. Если провайдер разрешает одну сессию, второй под получает отказ и переподключается с паузой; если разрешает несколько, оба работают параллельно. Корректность от числа экземпляров не зависит.
- **Отмена:** сначала компенсация (аннулировать ставку, вернуть заблокированную сумму), потом запрос провайдеру. Компенсация возможна только до принятия ставки, поэтому списанная сумма не возвращается.
- **Жёсткий срок ответа** отсчитывается от создания ставки, потому что клиент ждёт с этого момента. Рекомендация после срока игнорируется.

## Допущения

По условиям задачи большая часть поведения провайдера не описана; попутно появились вопросы к бизнесу и техлиду. На каждый пробел записан вопрос и предполагаемый ответ.

### Провайдер

| Вопрос | Допущение | На что влияет |
|---|---|---|
| Формат кадра и аутентификация? | JSON `{type, ticket_id, ts, payload}`; короткоживущий bearer-токен перед каждым подключением | Кодирование сообщений, получение токена |
| Что передаётся в `TICKET`? | Одиночная ставка: сумма, валюта, коэффициент (десятичными строками), id исхода, псевдоним клиента | Деньги не проходят через float, персональные данные не передаются |
| Каким сообщением приходит рекомендация? | `RECOMMENDATION {ticket_id, decision: ACCEPT\|DECLINE, reason?}`, без частичного принятия | Весь входящий поток |
| Есть ли подтверждения получения, как приходят ошибки? | Подтверждений нет. Ошибка: `ERROR {ticket_id?, ref_type?, code, message}`, где `ref_type` указывает, на какое сообщение ошибка | Финальное сообщение может потеряться при обрыве; поздние ошибки сопоставимы с тикетом |
| Идемпотентны ли сообщения по `ticket_id`? | Да: повторный `TICKET` возвращает исходную рекомендацию, повторные подтверждение, отказ и отмена ничего не делают | Основа повторной отправки |
| Возможны ли дубликаты, гарантирован ли порядок? | Дубликаты возможны, порядка между тикетами нет | Входящие обрабатываются параллельно |
| Сколько сессий можно на один аккаунт? | Одна; вторая отвергается; мёртвая сессия снимается примерно через 30 с | Передача сессии при деплое, число реплик |
| Привязаны ли сообщения к сессии или к аккаунту? | К аккаунту | Подтверждение можно отправить из другой сессии после деплоя |
| Как различить причины закрытия сессии? | HTTP 401/403 и 409 при подключении; коды 4000–4003 для планового закрытия, ошибки аутентификации, вытеснения и уже открытой сессии | Политика переподключения |
| Закрывает ли провайдер соединения сам? | Да, раз в несколько часов, отдельным кодом | Плановое закрытие: переподключение сразу, без алерта |
| Есть ли heartbeat? | WebSocket ping/pong каждые 20 с | Сколько обрыв может оставаться незамеченным |
| Переотправляет ли провайдер сообщения после переподключения, отменяет ли тикеты при обрыве? | Нет и нет; ожидающие тикеты интеграция отправляет повторно сама | Восстановление после обрыва |
| Сколько ждать рекомендацию и сколько провайдер ждёт подтверждение? | Рекомендация обычно до 2 с, максимум 5 с; срок интеграции 10 с; подтверждение принимается в течение 10 с | Сколько ждёт клиент |
| Есть ли лимиты частоты? | Не ниже десятков сообщений в секунду | Всплеск повторных отправок после переподключения |
| Можно ли отклонить ставку, которую провайдер рекомендовал принять? | Да, с причиной | Лимиты монолита проверяются при применении |
| До какого момента можно отменить ставку? | До расчёта; отмена идемпотентна; отмена неизвестного тикета считается выполненной | Отмена после падения до первой отправки безопасна |
| Что если подтверждение пришло поздно или отвергнуто? | Ошибка с `ref_type = CONFIRM_RECOMMENDATION` | Тикет уходит на ручной разбор |

Полные тексты вопросов и то, как ответы влияют на архитектуру, есть в [`docs/PROVIDER_QUESTIONS.md`](docs/PROVIDER_QUESTIONS.md). В коде такие места помечены `# ASSUMPTION:`.

## Kubernetes и эксплуатация

- **Пробы** на отдельном порту 9100:
  - `/startupz`: база доступна и все миграции применены. До этого ни один цикл не запускается.
  - `/livez`: каждый цикл вовремя отмечается. Недоступность провайдера или базы на неё не влияет, иначе любой сбой вызвал бы волну рестартов; зависший цикл приводит к рестарту.
  - `/readyz`: процесс может взять работу (стартовал, не завершается, база недавно отвечала). Наличие сессии с провайдером не требуется, иначе при rolling update новый под никогда не стал бы готовым.
- **SIGTERM:** процесс перестаёт читать и брать новые тикеты, дорабатывает прочитанные сообщения, отправляет уже закоммиченные ответы, закрывает сессию кодом 1001 и выходит с кодом 0, всё в пределах 10 с. Неотправленное остаётся в базе и уходит в следующей сессии.
- **Метрики** в формате Prometheus на `/metrics` того же порта. Метки только с низкой кардинальностью (состояние, исход, причина), без `ticket_id` и `bet_id`. Полный список в [`apps/risk_integration/runtime/metrics.py`](apps/risk_integration/runtime/metrics.py); главные:

  | Метрика | Что измеряется | На что ставить алерт |
  |---|---|---|
  | `risk_time_to_decision_seconds` | Время от создания ставки до применения решения (гистограмма) | p99 приближается к сроку ответа |
  | `risk_escalations_total`, `risk_escalation_failures_total` | Тикеты на ручном разборе; отказы провайдера, которые не удалось записать | Любой рост |
  | `risk_cancellations_total{reason}` | Отмены по причинам: срок, ошибка применения, отказ провайдера | Рост отмен по сроку |
  | `risk_compensation_failures_total` | Компенсации, которые не удались | Любой рост: просроченный тикет не отменяется |
  | `risk_unexpected_errors_total{loop}` | Неклассифицированные ошибки, изолированные одним сообщением или тикетом; процесс продолжает работу | Любой рост |
  | `risk_session_open`, `risk_sessions_ended_total{outcome}` | Наличие сессии; завершения сессий по исходу | Сессии нет ни на одном поде дольше нескольких минут; рост `auth_failed` |
  | `risk_inbound_queue_depth`, `risk_inbound_ignored_total`, `risk_frames_dropped_total` | Очередь входящих; дубликаты, поздние и нераспознанные сообщения | Рост `risk_sessions_ended_total{inbound_queue_full="true"}`: обработчики не успевают |

  Метрики по всей базе (тикеты по состояниям, возраст самого старого незавершённого) процесс не отдаёт: их должен считать SQL exporter, а не каждый под.

- **Логи** в stdout в JSON, с `ticket_id`, `bet_id` и `connection_id`. Конфигурация только из переменных окружения.

## Известные пробелы

- **Финальное сообщение может потеряться.** У подтверждения, отказа и отмены нет подтверждения получения. После переподключения интеграция один раз повторяет то, что ушло за последние 40 с перед обрывом; если и следующая сессия оборвётся в это время, сообщение может потеряться.
- **Нет ограничения частоты исходящих сообщений.** После долгого обрыва все ожидающие тикеты уходят подряд, так быстро, как позволяют сокет и база.
- **Таймауты базы** (2 с на запрос, 1 с на ожидание блокировки) действуют и на операции монолита внутри транзакции интеграции. Под реальные операции монолита они не подбирались.
- **Ошибка от провайдера может не сохраниться при долгом падении базы.** Если провайдер прислал ошибку (например, отказ в отмене), а база недоступна дольше трёх попыток записи, ошибка не попадает в тикет: остаются лог и метрика, тикет остаётся в прежнем состоянии.
